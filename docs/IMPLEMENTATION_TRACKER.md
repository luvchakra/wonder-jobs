## Deviations from the spec

- **Sources**: signed-in accounts search real public sources (company career sites via Greenhouse/Lever/Ashby boards, Remotive, Jobicy, Remote OK, Himalayas, Arbeitnow, Adzuna India with keys) through `server/jobs/providers.ts` and `/api/jobs/search`; postings are normalized deterministically (`services/jobs/normalize.ts`). LinkedIn, Indeed, Naukri, Foundit and Glassdoor have no public job APIs and are not searched — the product no longer claims them. The demo keeps the generated sample universe (`MockSourceAdapter`, ~1,100 canonical roles). No real scraping/API integration exists yet; the `JobSourceAdapter` interface is the seam for swapping in real adapters later (per §2: "typed service/interface and realistic mock adapter").
- **Persistence**: wired to Supabase (the project behind `NEXT_PUBLIC_SUPABASE_URL`; schema in `apps/web/supabase/migrations/`, applied via SQL Editor or `npm run db:migrate`). Server-side only: `server/supabase.ts` (service role), `server/state.ts` (per-tenant JSON document per client store → `wonderjobs.app_state`; all tables in the dedicated `wonderjobs` schema, exposed to the service role only), `SupabaseSecretStore` (`ai_provider_secrets`, ciphertext only), `action_audit` for external actions. The browser syncs every Zustand store through `store/remoteStorage.ts` (debounced PUTs, keepalive flush, localStorage cache/fallback). Requires `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SECRET_ENCRYPTION_KEY` in the deployment; without them the app runs local-only and says so on the Profile page. Verified live against the production Supabase project: state documents round-trip through both the local server and the Vercel deployment, BYOK keys land as ciphertext only (plaintext absent from the table), audit rows record, and the `wonderjobs` schema is reachable only with the service role. Schema applied via `POST /api/admin/migrate` (bearer = service-role key; runs only the bundled, checked-in migrations; auto-selects the IPv4 Supavisor pooler because the direct DB host is IPv6-only).
- **Auth**: Supabase Auth (email + password, magic link) with cookie sessions verified server-side (`server/session.ts`, `proxy.ts`); `getSession()` in `server/auth.ts` is the single seam. Without Supabase configured the app falls back to the anonymous per-browser cookie tenant. Earlier note, kept for history: no real login existed and the app assigned an anonymous per-browser session cookie; the `getSession()` seam in `server/auth.ts` is where it plugs in.
- **Scheduled runs**: there is no server-side cron yet. Due schedules fire from a client-side scheduler (`services/scheduler.ts`) while the app is open — same `WorkflowService.startRun` a server cron would call. Production needs that cron (e.g. a scheduled serverless function) so runs happen with the app closed.
- **External application**: Wonder does not submit on employers' sites (their forms need the candidate's own identity and consent). The `apply` stage is an audited hand-off: materials final, the employer's application page and a "Mark as submitted" action on the application, plus a submission reminder in the tracker.
- **Platform AI**: "WonderJobs AI" drafting uses a real model only when `WONDERJOBS_AI_KEY` is set on the server (Anthropic, `claude-sonnet-5` by default); otherwise deterministic templates, stated on the AI settings page. Matching, ranking and quality are always deterministic and explainable.
- **Google sign-in**: the code path is complete, but the provider must be enabled in Supabase with a Google OAuth client (see README). Until then the button shows a clear "not switched on yet" message.
- **Support mailbox**: contact messages are always stored in `wonderjobs.contact_messages` (Supabase → Table Editor). An email copy is optional and configured per deployment: `CONTACT_NOTIFY_EMAILS` names the recipients, `RESEND_API_KEY` turns on real delivery; without the key, the notification is logged instead of sent.
- **Email delivery**: application-level follow-up emails go through the full confirm/idempotency/audit ledger but delivery is mocked (no mail provider connected). The send step in `components/applications/FollowUpAction.tsx` is where a provider plugs in.

## Working notes

- Real data end to end. The generated job universe is now demo-only. Signed-in runs search live sources (see README "Job sources"): the search stage calls `/api/jobs/search` per enabled source (server-side fetch + normalize, Next data cache 15 min + 10 min memory cache), reports per-source evidence including "Needs setup" for credentialed sources, and the rest of the pipeline (dedupe, understand, match, quality, rank, prepare, review, apply, track, learn) runs unchanged on the real postings. Matching gained a remote-region check (`remoteOpenTo`) so "remote, US only" no longer scores as a perfect location fit for an India-based candidate. Onboarding now collects headline, level, years, skills and industries (the Career DNA that scoring needs); the catalog persists per account (top 300 by score plus saved, descriptions trimmed) so jobs survive reloads. Apply stage → honest hand-off; continuing past pending approvals records them as "not approved" (the button says "Continue without N pending"). A run waiting for the candidate now survives a closed tab: `WorkflowEngine.hydrate` keeps `WAITING_FOR_USER` and `continueFromUser` re-runs the waiting stage with the wait already answered (unit-tested). Match calibration on live postings: skills are read from the posting text with inflection-aware stems and capped denominators, undisclosed salary is near-neutral, remote roles restricted to another region are capped at "worth considering", fit thresholds 82/68/55, and prepare fills from the top of the shortlist when there are no strong matches. Verified in a browser against the real Supabase project and live sources: 110 real jobs → shortlist → 3 prepared → review (across a browser restart) → 3 hand-offs approved and executed → applications carry "Apply on <employer>'s site, then mark as submitted" plus a reminder. WonderJobs AI → real model when the platform key is set; templates otherwise, labelled.

- Real accounts + demo mode. The deployment previously showed the seeded sample candidate to everyone. Now: `/sign-up` and `/sign-in` (Supabase Auth: password or magic link; PKCE callback at `/auth/callback`), a route proxy that requires a session for `/app/*` and `/onboarding` (refreshing expired tokens, mirroring the user id into a JS-readable cookie), API routes returning 401 without a session, stores that start empty for a new account (`EMPTY_DNA`, no seeded runs/applications/notifications) with onboarding gated in `AppShell`, matches scored against the account's own Career DNA (re-scored on every DNA change), local state namespaced per user, and sign-out that revokes, clears and forgets local copies. The previous experience lives on as **Demo** under the avatar menu (`/demo` sets `wj_demo`; seeded once per device; device-only, no server sync; `/demo/exit`). Landing CTAs point at sign-up/sign-in/demo. Verified end to end with Playwright against the real Supabase project: guard → demo → exit → sign-in → onboarding → empty real dashboard with the account name → state synced under the user id → sign-out clears cookies and re-guards. Supabase project has "Confirm email" on (`mailer_autoconfirm: false`) and default Site URL; see README for the dashboard settings to review.

- Performance pass (spec §40, "pages should load immediately"). Root causes found by measurement: every page load blocked on eight sequential-per-store `/api/state/<store>` round trips (each 200–1,400 ms in production because Vercel functions ran in `iad1` while Supabase lives in `ap-south-1`), each save cost three database round trips per store, `computeQuality` spent ~60 ms per load constructing `Intl` formatters, and nothing was cached between navigations. Fixes: (1) `remoteStorage` is now object-level and local-first — a local copy hydrates every store synchronously inside a layout effect, so the hydrated tree replaces the SSR skeleton before first paint; the server is consulted once per page load in a single `GET /api/state`, stores whose server copy differs are re-hydrated in place, unsynced local edits are tracked in `wj.sync.dirty` and win; (2) writes serialize on a 120 ms debounce, identical values are dropped, and all dirty stores go up in one `PUT /api/state` (RPC `wonderjobs.put_state`, migration `0002`, one database round trip; falls back to the old path until the migration is applied); (3) the app layout starts the state request from inline HTML before any JS is parsed; (4) `vercel.json` pins functions to `bom1`; (5) shared `Intl.DateTimeFormat` instances in matching and formatting; (6) React Compiler on, `experimental.staleTimes` keeps visited product segments in the client router cache, and the four `[id]` routes declare `generateStaticParams` so their shell is prefetched and CDN-cached instead of invoking a function per visit; (7) workflow-engine hydration and BYOK status refresh moved after first paint. `performance.mark("wj:boot"/"wj:hydrated")` are emitted for field measurement.

- Vercel deployment protection was narrowed from `all_except_custom_domains` to `preview` so the production URL is publicly reachable (a marketing site behind Vercel SSO would have been invisible to visitors); previews stay protected. Revert in Vercel → Settings → Deployment Protection if that was intentional.

- Repo was moved from the repo root into `apps/web` (npm workspaces) after the connected Vercel project's Root Directory (`apps/web`) was discovered to not exist, causing every prior deploy to fail at the clone step. `vercel.json` in `apps/web` pins the build command.
