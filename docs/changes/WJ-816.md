# WJ-816: A search no longer waits on work it doesn't need

- **What:** Four changes to `server/jobslake/core.ts::search` (and `cache.ts`), none of which changes what a search returns:
  - Old cached answers are dropped after the response is sent, not while the search waits (`pruneAnswersIfDue`).
  - A posting served from the search cache is not stored again: only postings from sources that answered just now are written to the warm pool and the company directory.
  - The opening reads (gateway stamp, sources, health and keys, banned companies, hidden listings) run together.
  - The closing writes (runs, search cache, companies, warm pool) and the warm pool read run together.
- **Why:** Measured by the E2E session on a fresh production build against the real project (2026-11-21, through its proxy, source answering from cache): first search 17.7 s, later ones about 3 s, with the source itself taking almost nothing.
  - First search: 7.4 s was the delete of old cached answers, 4.6 s the opening reads one after another, 4.8 s the closing writes and the warm pool load (3.2 s for 1,000 postings, 5.8 MB).
  - Every search: 1.3 to 1.5 s re-storing postings that came from the cache, and about 1 s of opening reads in sequence.
- **Notes:**
  - Expected from those figures: roughly 6 to 7 s cold (bounded by the warm pool load) and a little over 1 s for a cached search. To be re-measured the same way after merge.
  - Not changed: the warm pool still loads up to 3,000 full postings per module on a cold instance. That is the next cost to look at.
  - Tests: `core.test.ts` now checks that a fully cached search stores nothing again and doesn't prune while it waits. All WorksLake tests pass.
