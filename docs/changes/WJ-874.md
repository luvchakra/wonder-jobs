# WJ-874 · Hiring and the database guard · DONE

**What:**
1. When Hiring's first read of the workspaces fails, the page now says "Couldn't load Hiring" with Try again, instead of loading forever.
2. The database guard writes one line to the server log when it holds requests back.
**Why:**
- The 2026-11-26 nightly (run 45750722586) failed HIRE-008, and HIRE-004 failed in the retry that followed.
- On that retry /app/hiring sat on "Loading…" for 20 s: one failed `/api/hiring` read left the page on `PageLoading` for good, with only a toast.
- The run also pointed to database reads stalling between 03:51 and 03:57 UTC, but nothing in the log could confirm it. The shared-layer session asked for both changes (2026-11-26).
- A re-run of the hiring and jobslake specs on main 7603f93 passed (22/22, 0 flaky).
**Notes:**
- `src/app/app/hiring/page.tsx` + `components/hiring/loadState.ts` (`hiringLoadState`):
  - Before any data, a failed read shows the error with one control, Try again.
  - After data has loaded, a failed reload keeps the page and shows a toast, as before.
- `server/dbGuard.ts` reports these events:
  - a deadline missed
  - a refusal (queue full, or the breaker open)
  - the breaker opening
  - a wait of 2 s or more for a slot
- Each event is one `[dbGuard] <why>: active= waiting= open= failures= timedOut= refusedBusy= refusedBreaker=` line, at most once every 10 s. It holds counts only: no URL, query, key or tenant (tested). The line also appears in Vercel's logs.
- Tests:
  - `loadState.test.ts`
  - `dbGuard.test.ts`: two new tests, for the breaker line with its throttling and no request details, and for the slow-wait line.
  - HIRE-001 now fails the first `/api/hiring` read once, expects "Couldn't load Hiring", and presses Try again.
